# Архитектура проекта

Проект — учебный. Его цель — потренироваться в **простой модульной архитектуре
фронтенда** (Simple Architecture) на небольшом, но реалистичном приложении:
каталоге сериалов на основе [TVmaze API](https://www.tvmaze.com/api).

> ⚠️ **Важно.** Под названием «Simple Architecture» в сообществе встречаются
> немного разные варианты. Описанная ниже структура (`app` → `features` →
> `services` → `shared`) — это вариант, принятый **в этом проекте**. Если вы
> учитесь по конкретному курсу или статье, сверьте с ними названия слоёв и
> правила и поправьте этот документ и `.oxlintrc.json`.

---

## 1. Главная идея

Код делится на **слои**. Каждый слой может импортировать только из слоёв,
которые ниже его. Внутри слоёв `features` и `services` код разбит на
**модули**: изолированные папки с публичным API.

```
┌──────────────────────────────────────────────┐
│ app       композиция: маршруты, layout,      │
│           провайдеры, конфигурация роутера   │
├──────────────────────────────────────────────┤
│ features  пользовательские сценарии:         │
│           show-list, show-search, ...        │
├──────────────────────────────────────────────┤
│ services  переиспользуемая бизнес-логика:    │
│           show (модель, запросы, карточка)   │
├──────────────────────────────────────────────┤
│ shared    инфраструктура без бизнес-смысла:  │
│           api-клиент, ui-kit, i18n, утилиты  │
└──────────────────────────────────────────────┘
        импорт разрешён только сверху вниз ↓
```

В отличие от Feature-Sliced Design, здесь нет слоёв `pages`, `widgets` и
`entities`. Страницы — это маршруты в `app/routes`. Переиспользуемая
предметная логика живёт в `services`.

## 2. Структура папок

```
src/
├── app/                        # Слой композиции
│   ├── main.tsx                # Точка входа (подключена в index.html)
│   ├── app.tsx                 # Провайдеры: QueryClient + Router
│   ├── query-client.ts         # Настройки TanStack Query
│   ├── router.tsx              # Создание роутера и регистрация типов
│   ├── routeTree.gen.ts        # ⚙️ Генерируется плагином, не редактировать
│   ├── routes/                 # File-based маршруты TanStack Router
│   │   ├── __root.tsx          #   корневой layout + devtools
│   │   ├── index.tsx           #   "/"  — каталог и поиск
│   │   └── shows/$showId.tsx   #   "/shows/:id" — карточка сериала
│   ├── layout/                 # Каркас приложения (шапка, 404, скелетоны)
│   └── styles/index.css        # Tailwind + тема shadcn
│
├── features/                   # Пользовательские сценарии
│   ├── show-list/              #   каталог с пагинацией
│   ├── show-search/            #   поле поиска + результаты
│   ├── show-details/           #   подробная информация о сериале
│   └── language-switcher/      #   переключение языка
│
├── services/                   # Переиспользуемая бизнес-логика
│   └── show/
│       ├── model/              #   доменные типы и мапперы DTO → модель
│       ├── api/                #   queryOptions-фабрика (ключи + запросы)
│       ├── ui/                 #   ShowCard, ShowGrid, ShowPoster, ...
│       └── index.ts            #   ПУБЛИЧНЫЙ API модуля
│
└── shared/                     # Инфраструктура
    ├── api/                    #   http-клиент, ApiError, эндпоинты TVmaze и DTO
    ├── config/                 #   переменные окружения
    ├── i18n/                   #   настройка i18next и словари (ru, en)
    ├── lib/                    #   утилиты (cn, htmlToText, хуки)
    └── ui/
        ├── kit/                #   компоненты shadcn/ui (генерируются CLI)
        ├── error-state.tsx
        └── empty-state.tsx
```

## 3. Слои подробно

### `shared`: инфраструктура

Код, который **ничего не знает о предметной области** и мог бы без изменений
переехать в другой проект.

- `shared/api`: `createHttpClient`, `ApiError`, `tvmazeApi` и DTO-типы
  (ответ сервера «как есть»). Здесь только транспорт, без маппинга.
- `shared/ui/kit`: примитивы shadcn/ui (`Button`, `Card`, ...). Их создаёт CLI
  shadcn, вручную их можно дорабатывать.
- `shared/i18n`: инициализация i18next и словари.
- `shared/lib`: мелкие утилиты и хуки.
- `shared/config`: единственное место, где читается `import.meta.env`.

**Может импортировать:** только `shared` и npm-пакеты.
Внутри `shared` можно импортировать файлы по прямому пути
(`@/shared/ui/kit/button`): у `shared` нет инкапсуляции, это набор
независимых кусочков.

### `services`: переиспользуемая бизнес-логика

Модуль сервиса описывает **сущность предметной области** и всё, что нужно
нескольким фичам для работы с ней.

Пример: `services/show`:

| Папка   | Что внутри                                                         |
| ------- | ------------------------------------------------------------------ |
| `model` | `Show`, `ShowDetails`, `CastMember` и мапперы `TvmazeShowDto → Show` |
| `api`   | `showQueries`: фабрика `queryOptions` с ключами кэша                 |
| `ui`    | `ShowCard`, `ShowGrid`, `ShowPoster`, `ShowRating`, `ShowStatusBadge` |

Зачем нужна доменная модель, если есть DTO? Чтобы компоненты не зависели от
формы ответа сервера. Если TVmaze поменяет поле, правка будет в одном маппере.
Заодно маппер очищает HTML в `summary` и подбирает запасные значения.

**Может импортировать:** `shared` и другие сервисы (только через их `index.ts`).

### `features`: пользовательские сценарии

Фича — это то, что **делает пользователь**: листает каталог, ищет, смотрит
подробности, меняет язык.

Правила:

1. **Фичи не импортируют друг друга.** Если двум фичам нужен общий код, он
   переезжает в `services` (бизнес-логика) или в `shared` (инфраструктура).
2. **Фича не знает, где хранится её состояние.** `ShowList` получает `page`
   и `onPageChange` через props. Хранить номер страницы в URL решает `app`.
3. **Наружу торчит только `index.ts`.**

**Может импортировать:** `services` (через `index.ts`) и `shared`.

### `app`: композиция

Здесь фичи собираются в работающее приложение:

- провайдеры (`QueryClientProvider`, `RouterProvider`);
- маршруты: **маршрут — это страница**. Он читает параметры URL,
  валидирует их, запускает лоадеры и решает, какие фичи и как показать;
- общий layout (шапка с `LanguageSwitcher`).

Пример композиции в `app/routes/index.tsx`:

```tsx
<ShowSearchInput value={q} onChange={(query) => navigate({ search: { q: query } })} />
{q ? <ShowSearchResults query={q} /> : <ShowList page={page} onPageChange={...} />}
```

`show-search` и `show-list` ничего не знают друг о друге и об URL.
Связывает их только маршрут.

**Может импортировать:** всё.

## 4. Публичный API модулей

У каждого модуля в `features/*` и `services/*` есть `index.ts`. Импорт
снаружи разрешён **только** через него:

```ts
// ✅ правильно
import { showQueries, ShowGrid } from '@/services/show'

// ❌ нельзя: лезем во внутренности модуля
import { showQueries } from '@/services/show/api/show-queries'
```

Внутри модуля файлы импортируют друг друга **относительными путями**
(`../model/types`).

Что это даёт: внутреннюю структуру модуля можно менять как угодно, пока не
меняется его `index.ts`.

## 5. Автоматическая проверка границ

Правила слоёв проверяет линтер (`npm run lint`) через правило
`no-restricted-imports` в [`.oxlintrc.json`](../.oxlintrc.json):

| Откуда        | Запрещено                                                        |
| ------------- | ---------------------------------------------------------------- |
| везде         | глубокие импорты `@/features/x/...`, `@/services/x/...`           |
| `shared/**`   | `@/app`, `@/features`, `@/services`                              |
| `services/**` | `@/app`, `@/features`                                            |
| `features/**` | `@/app`, **любые** другие фичи (`@/features/...`)                 |

Пример ошибки:

```
error eslint(no-restricted-imports): '@/features/show-list' import is restricted...
help: Фичи изолированы и не импортируют друг друга. Компонуйте их в app.
```

> Ограничение: правило проверяет только импорты через алиас `@/`.
> Относительный импорт вида `../../show-list` формально пройдёт, поэтому
> между модулями всегда используйте `@/`.

## 6. Потоки данных

### Каталог и поиск (`/`): `useQuery` внутри фичи

```
URL ?page=2&q=...
   │  validateSearch (app/routes/index.tsx)
   ▼
HomePage ── page ──► ShowList ── useQuery(showQueries.list(1)) ──► tvmazeApi.getShows(1)
        └── q ─────► ShowSearchResults ── useQuery(showQueries.search(q))
```

- Номер страницы и запрос хранятся **в URL**, поэтому ссылкой можно
  поделиться, а кнопки «Назад/Вперёд» в браузере работают.
- `placeholderData: keepPreviousData`: при смене страницы старые карточки
  остаются на экране, пока грузится новая страница.
- Поле поиска обновляет URL с задержкой (`useDebouncedValue`) и `replace: true`,
  чтобы не засорять историю браузера.

### Карточка сериала (`/shows/$showId`): лоадер роутера + `useSuspenseQuery`

```
Переход по ссылке (или наведение: defaultPreload: 'intent')
   │
   ▼
loader: queryClient.ensureQueryData(showQueries.detail(id))   ← app
   │   404 → notFound() → notFoundComponent
   │   ошибка → errorComponent (с кнопкой «Повторить»)
   ▼
ShowDetails: useSuspenseQuery(showQueries.detail(id))         ← feature
```

Почему здесь иначе, чем в каталоге:

- Данные начинают грузиться **до** рендера, уже при наведении на карточку.
- Внутри фичи нет состояний `isPending` и `isError`: данные гарантированно есть.
- Роутер берёт на себя pending, error и not found.

Для каталога такой подход не подходит: при смене запроса роутер показал бы
`pendingComponent` вместо всей страницы, и поле поиска потеряло бы фокус.

### Ключи кэша

Все ключи создаются в одной фабрике `showQueries`:

```
['shows']                         ← showQueries.all()
['shows', 'list']                 ← showQueries.lists()
['shows', 'list', 0]              ← showQueries.list(0)
['shows', 'search', 'girls']      ← showQueries.search('girls')
['shows', 'detail', 1]            ← showQueries.detail(1)
```

Иерархия позволяет инвалидировать данные группами:
`queryClient.invalidateQueries({ queryKey: showQueries.lists() })`.

## 7. Как добавить новую функциональность

**Пример: «Расписание эфиров на сегодня»** (`GET /schedule`).

1. **shared/api**: добавить DTO `TvmazeEpisodeDto` в `tvmaze/types.ts` и метод
   `getSchedule()` в `tvmazeApi`.
2. **services**: если эпизоды понадобятся нескольким фичам, создать
   `services/episode` с моделью, маппером, `episodeQueries` и `index.ts`.
   Если только одной фиче, всё это можно держать внутри фичи
   (см. правило ниже).
3. **features**: создать `features/schedule/ui/schedule.tsx` и
   `features/schedule/index.ts`.
4. **i18n**: добавить ключи `schedule.*` в `shared/i18n/locales/ru.ts`.
   TypeScript подскажет, что их не хватает в `en.ts`.
5. **app**: создать маршрут `app/routes/schedule.tsx`, отрендерить в нём
   `<Schedule />` и добавить ссылку в `AppLayout`.
6. Проверить: `npm run lint && npm run build`.

### Правило «когда выносить в services»

> Сначала код живёт **внутри фичи**. В `services` он переезжает, когда
> понадобился **второй** фиче.

Так `services` не превращается в свалку «на всякий случай».

## 8. Соглашения

- Имена файлов в `kebab-case`, компоненты в `PascalCase`.
- Компоненты объявляются как `export const X = () => ...`. Исключение —
  маршруты: там компоненты объявлены функциями ниже `Route`, чтобы их можно
  было использовать до объявления.
- Тексты интерфейса только через `t('...')`, без строк прямо в JSX.
- DTO (`*Dto`) не выходят за пределы `shared/api` и мапперов в `services`.
  Компоненты работают только с доменными моделями.
